# Agent integration guide

How an AI agent integrates Valyd: read the machine-readable docs, ask the developer the right
questions, pick the lane, and call the APIs. (Prefer callable tools instead? See the
[Valyd MCP server](/ai/mcp-setup).)

## Integration decision flow (start here)

<Callout type="info">
  **If you're an agent scaffolding this in a tool like Lovable, Cursor, or Claude Code: ASK the
  developer the questions below BEFORE writing code.** Each answer pins one path, one credential,
  and one doc page to fetch and follow. Invent nothing — the credentials, endpoints, and page
  names here all come from the docs those pages link to.
</Callout>

Ask, in order:

### 1. Do you already have an app, or are you starting fresh?

Context only — it tells you where the "Login with Valyd" button and the keys go. No branch; keep
going.

### 2. Do you have — or want — an organization (a team/workforce you onboard and control)?

- **Yes, and you want to control members** — add people, decide who can log in, assign roles →
  **Organizations path**. You onboard members by **face-activation**; they then sign in with
  **Login with Valyd**. Roles are **owner / admin / developer / member**. Track exactly who logged
  in via the **`valyd_org_member_id`** claim (its value is that member's `vmem_…` id) on the OIDC
  userinfo response and ID token. Billing is **unlimited verifications on a per-active-member
  monthly plan** (a member is billable only once they scan their face; 14-day trial first; current
  price at [/docs/organizations/billing](/docs/organizations/billing)).
  → Credential: **`client_id` + `client_secret`** (Login with Valyd) **plus** the Members API
  (headers `X-Client-Id` / `X-Client-Secret`, server-side only).
  → Fetch [**Organizations**](/docs/organizations).
- **No org / no member control** → continue.

### 3. Do you just want to read — or verify — a user who signs in with Valyd?

They log in, and you either read the proofs their account already holds, or add a check that saves
to **their** Valyd account.
→ **Account API — "With the user's token"**. Read proofs (`id_verified`, age bands, licenses) for
free and instantly; run any check with the token attached and the passed proof saves to their
Valyd ID for reuse. The PII stays with Valyd — you get proofs, not raw data.
→ Credential: OIDC Bearer **`valyd_access_token`** (obtained via Login with Valyd).
→ Fetch [**With the user's token**](/docs/user-token).

### 4. Do you want to run verification checks? Pick one of two lanes.

The verification choice is **Managed by Valyd vs Verify Fresh** — decided by login and which checks
you need:

**Managed by Valyd** — signing the user in, want proofs saved to their account, or need ID/KYC,
face match, age, professional license, or location:

- The user **signs in with Valyd**, and you run a hosted session with their **`valyd_access_token`**.
  **Every check is available** here, and passed proofs save to their Valyd ID while the raw
  identity data stays encrypted with Valyd — you get the decision plus reusable proofs, never raw
  PII. One call — `sessions.create({ workflowId, valydAccessToken, redirectUrl })`.
  → Credential: App **`X-API-Key`** + `workflow_id` + the user's **`valyd_access_token`**.
  → Fetch [**Managed by Valyd**](/verifications/managed) (and
  [With the user's token](/docs/user-token) · [Hosted delivery](/verifications/hosted)).

**Verify Fresh** — a one-off check with **no login** and nothing saved to an account:

- Runs the **liveness + face-uniqueness + anti-spoof** family **only**, on Valyd's hosted page **or**
  as direct API calls from your backend. The result returns to your system.
  → Credential: App **`X-API-Key`**. → Fetch [**Verify Fresh checks**](/verifications/standalone).

<Callout type="warning">
  **ID/KYC, face match, age, professional license, and location are no longer self-serve direct
  checks.** They run only through **Managed by Valyd** — a signed-in user's hosted session. Verify
  Fresh covers liveness, anti-spoof, and face uniqueness only.
</Callout>

### 5. Want it all in one flow?

The user signs in **and** you run several checks on Valyd's hosted UI, with proofs saved to their
account — that **is** Managed by Valyd:
→ `sessions.create({ workflowId, valydAccessToken, redirectUrl })`. One flow = login-tied
verification + Valyd's hosted UI + proofs on the account.
→ Credential: App **`X-API-Key`** + `workflow_id` (+ the user's `valyd_access_token`). → Fetch
[**Managed by Valyd**](/verifications/managed) and [**Hosted delivery**](/verifications/hosted).

### Then clarify (as relevant)

Once the path is set, ask whichever of these apply and fetch the named page:

- **Which checks do you need?** ID / KYC, face match, age (returns age *bands* like `is_18_plus` —
  never the DOB), professional license, and location / EVV presence run **only through Managed by
  Valyd** (a signed-in user's hosted session). Liveness, anti-spoof, and face uniqueness
  (one-person-one-account dedup) also run tokenless via **Verify Fresh**.
  → [Verification types](/verifications/types)
- **Reusable identity (KYC-reuse)?** Save a passed check as a proof so you never re-verify that
  person again — that's **Managed by Valyd**, needs the user's `valyd_access_token`. A one-off
  **Verify Fresh** liveness/uniqueness check saves nothing. → [With the user's token](/docs/user-token)
- **How should results be delivered?** Async signed **webhook** (Managed by Valyd, or Verify Fresh
  hosted) or synchronously in the **API response** (Verify Fresh direct calls).
  → [Webhooks](/verifications/webhooks)
- **Do you need RAW identity data** (DOB, document number, address)? That requires the explicit
  **consent flow** — the user approves on their own device; otherwise you only ever receive proofs
  / verified-status. → [Request user data](/docs/request-data)
- **Which login scopes?** `profile` (legal name, country, verified status), `verifications`
  (proofs / badges), `email`, `doctor_license`. → [Scopes](/docs/scopes)
- **Professional license check?** Runs through **Managed by Valyd** — a signed-in user's hosted
  session; the name comes from the account and the verified badge saves to their Valyd ID. →
  [Managed by Valyd](/verifications/managed)
- **Drop-in button or your own OIDC library?** The "Sign in with Valyd" button
  ([Login with Valyd](/docs)) or any OIDC library via discovery ([OIDC](/docs/oidc)).
- **Where do the credentials come from? (important for agents)** A human must create the app and
  keys in the Developer Portal (https://dev.valyd.work) — an agent **cannot** mint
  `client_id` / `client_secret` / API key / `workflow_id`. **Pause and ask the developer for them;
  never guess.** → [Dev portal setup](/docs/create-project)
- **Billing model?** Organization = **unlimited verifications on a per-active-member monthly plan** (a
  member becomes active, and billing starts, the moment they face-scan; current price at
  [/docs/organizations/billing](/docs/organizations/billing)); standalone / non-org =
  pay per check. → [Organizations](/docs/organizations)

**Agents scaffolding in a tool like Lovable/Cursor: ASK these questions before writing code; then
fetch the named page's `.md` and follow it.** The exact `.md` fetch URL for each page is listed in
[`llms.txt`](https://docs.valyd.work/llms.txt) (e.g. `.../docs/organizations.md`,
`.../docs/user-token.md`, `.../verify/standalone.md`, `.../verify/hosted.md`) — see Step 1.

## Step 1 — Read `llms.txt` first

```bash
curl -sL https://docs.valyd.work/llms.txt
```

One fetch gives the agent the full docs hierarchy, base URLs, credential rules, and links to
every page as clean Markdown. Fetch individual `.md` pages on demand rather than loading the
full corpus, unless you need everything — then use
[`llms-full.txt`](https://docs.valyd.work/llms-full.txt). The OpenAPI 3.1 specs
([Valyd ID](https://docs.valyd.work/openapi/valyd-id.json) ·
[Verification APIs](https://docs.valyd.work/openapi/valyd-verify.json)) and the
[Postman collection](https://docs.valyd.work/valyd-postman-collection.json) are listed on
[the agent-readable docs page](/agents).

## Step 2 — Pick a lane

**Verify Fresh (App API key, no login).** For a one-off liveness, anti-spoof, or face-uniqueness
check: call it with `VALYD_API_KEY` — or send the person to the hosted page — and the result comes
back to your system. Nothing is saved to a Valyd account, and the data is yours to manage and
protect. Start at the [Verification quickstart](/verifications/quickstart).

**Managed by Valyd (a signed-in user's token).** The user signs in with Valyd (OAuth 2.0 / OIDC);
your agent acts with their access token. Read the proofs their Valyd ID already holds
(`id_verified`, age bands, licenses) instead of re-verifying, and run any check — ID/KYC, face
match, age, license, location — on a hosted session with the token attached; the passed proof saves
to their account for reuse everywhere and the raw identity data stays encrypted with Valyd. Start at
[Managed by Valyd](/verifications/managed) and the [Valyd ID docs](/docs). Need raw personal data?
Use the [human-in-the-loop consent flow](/docs/request-data) — the user approves the exact fields in
their Valyd app and the values arrive sealed to your key.

## Step 3 — Call the APIs

Follow the pages `llms.txt` points to. Two golden rules keep the products straight:

<Callout type="warning">
  **The two golden rules**

  1. The **Account API never runs a check** — a user token only *reads* proofs the account
     already holds.
  2. A **check never touches an account** unless the user's token is attached to the call —
     API-key-only checks return results to you and save nothing to any Valyd ID.
</Callout>

## Notes for agents

- **Credentials cannot be created via API.** Pause and ask a human to supply `client_id`,
  `client_secret`, and `VALYD_API_KEY` before making auth calls.
- Token exchange and webhook signature verification must run server-side — never expose
  `client_secret` to a browser.
- Prefer the clean `.md` URLs listed in `llms.txt` over scraping HTML pages.
- Prefer **proofs** over raw data where they suffice — request `is_18_plus`, not `dob`.

Prefer tools over raw HTTP? [Connect the MCP server](/ai/mcp-setup) instead.
